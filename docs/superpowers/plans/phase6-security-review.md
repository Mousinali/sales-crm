# Security review against req.md §13 — Phase 6

A line-by-line walk of every bullet in req.md §13 (Authentication and
Security), each marked Pass / Fail / Partial with the file and evidence that
proves it. Every Fail found here was fixed in this same task, not filed away
— per the plan's own rule, "perform a security review before company use"
means closed, not just written down.

| Store password hashes using Argon2id or bcrypt with an appropriate work factor | **Pass** | `src/lib/auth/passwords.ts:5` — `argon2.hash(plain, { type: argon2.argon2id })`. Default work-factor params from the `argon2` package, not weakened. |

| Use HTTPS in production | **Partial — app-ready, infra-pending** | The `secure` cookie flag above is already conditioned correctly on `NODE_ENV`. Actual TLS termination is a deploy/ops task (reverse proxy or platform), not application code — tracked in `phase6-production-readiness.md` §2. Nothing to fix in this codebase. |
| Implement session expiration and revocation | **Pass** | `src/lib/auth/session.ts` — sessions carry `expires_at` (set from `SESSION_TTL_HOURS` at creation) and every session lookup filters `AND s.expires_at > now()`; `revokeAllSessions(userId)` and `revokeSession(token)` both exist and are exercised (user deactivation, access reset, logout). |
| Rate-limit login and sensitive operations | **Fail → fixed** | No rate limiting existed anywhere in the codebase before this task. Added `src/lib/auth/rateLimit.ts`, an in-memory fixed-window counter (5 attempts / 15 minutes), wired into both `POST /api/auth/login` and `POST /api/auth/change-password` (the latter added after a fresh-context review pointed out it was a second, unthrottled password oracle for anyone holding a stolen session cookie). **Keyed by email alone for login, by the session's own verified user id for change-password — never by a client-supplied value.** An earlier version also keyed login by the client's `X-Forwarded-For` header; that was removed after an automated review caught that this app has no trusted-proxy convention to anchor it to, so an attacker could spoof a fresh IP on every request and bypass the limit entirely. The accepted tradeoff of email-only keying: a third party who knows a victim's email can lock that one account out of login — `req.md` only asks to rate-limit login, not to survive a targeted denial-of-service against one identifier, and this is the standard cost of any email-keyed lockout policy. The store went through several rounds of hardening after the first fix, each round's automated review finding that the *previous* round's eviction rule was itself gameable from a new angle (unbounded growth → a hard cap with oldest-first eviction → that could un-block an attacker mid-lockout → evict only non-blocked entries instead → that could still reset a target's in-progress counter via a flood of junk keys → evict only truly-fresh single-attempt entries → an attacker can always *manufacture* single-attempt keys, including evicting their own counter to reset it indefinitely). The pattern across every round was the same: any eviction decision keyed on an entry's own state is exploitable, because the attacker chooses which keys exist. The fix that actually closes the class: **no eviction at all.** The store's size is bounded instead by throttling how many brand-new identifiers can be *admitted* per 60-second window (500), independent of which key — once that budget is spent, only new keys are refused; every identifier already being tracked keeps counting normally, untouched. **Scope note unchanged:** the store is per-process memory — correct for a single app instance, and would need a shared store (Redis or similar) for a multi-instance deployment; this task does not add that dependency speculatively. |
| Validate and sanitize all incoming data | **Pass** (gap closed in Task 4) | Every mutating route validates its body with a Zod schema. Task 4's sweep found and fixed the one real gap (`visitDate`/`startTime`/`objective` accepting an empty string, crashing Postgres with a raw 500) — see that task's commit. No further mismatches against req.md's field lists for leads/visits/tasks/email announcements/users/services/auth. |
| Use parameterized SQL to prevent SQL injection | **Pass** | `grep -rn 'pool\.query(\`[^$]*\${' src` turns up exactly three matches, and all three are the standard-safe pattern of interpolating *placeholder lists or column names* (never user data) into the query text, with the actual values still passed through the `$N` parameter array: `src/lib/leads/services.ts:36` (`VALUES ($1,$2),($1,$3)...` built from a fixed template, ids passed as params), `src/lib/leads/update.ts:92` and `src/lib/users/update.ts:30` (dynamic `SET col = $N` lists built from a hardcoded, non-user-controlled set of column names in each function's own `set()` helper calls). No raw string concatenation of a request-supplied value into SQL text anywhere. |
| Apply server-side authorization checks on every protected operation | **Pass** | Cross-checked against Task 1's permission matrix (`docs/superpowers/plans/phase6-permission-matrix.md`), which now has a passing test for every Denied/Allowed-if-owner cell across Phases 2–5, plus Phase 5's own final-review fix (task assignment/leadId can no longer bypass server checks via direct API calls) and Task 2's concurrency-safe locking. |
| Protect state-changing operations against CSRF as appropriate to the session architecture | **Pass** | The session cookie is `SameSite: "lax"`, which blocks the cookie from being attached to a cross-site request other than a top-level GET navigation — covering both a classic cross-site form `POST` and a cross-site `fetch()`/XHR alike, since `SameSite` governs the cookie, not the request method. Confirmed no `GET` handler anywhere mutates state, and there are no Server Actions or native `<form action>` submissions that would bypass this. No separate CSRF token is added; `SameSite=Lax` is the appropriate, proportionate control for this cookie/request architecture. Two residual caveats worth naming rather than treating as gaps: `SameSite` does not isolate same-site sibling subdomains from each other (not a concern today — this app has none), and this reasoning depends on "no state-changing GET" remaining true as the app grows. |
| Prevent open redirects and validate file uploads if uploads are added | **Pass / N/A** | Every `redirect(...)` call in the app (`grep -rn "redirect(" src/app`) uses a hardcoded literal path (`/dashboard`, `/login`, `/change-password`) — none take a user-controlled redirect target, so there is no open-redirect surface at all. No file-upload functionality exists anywhere in Phases 1–5, so the file-upload-validation clause is vacuously satisfied ("if uploads are added" — they haven't been). |
| Keep secrets in server-side environment variables | **Pass** | Cross-checked against Task 5's env-var audit: `DATABASE_URL` and all `SMTP_*` credentials are read only in server-only modules (`src/lib/db.ts`, `src/lib/email/sendEmail.ts`), never passed to a Client Component or exposed via a `NEXT_PUBLIC_*` variable. |
| Do not log passwords, session tokens, or sensitive credentials | **Pass** | `grep -c "console\.\(error\|log\)" src` returns zero matches anywhere in the app — nothing is logged to begin with, so nothing sensitive can leak that way. Separately, `src/lib/users/create.test.ts` and `src/lib/users/resetAccess.test.ts` both already assert the generated temp password never appears in the `audit_logs.details` JSON. |

| Back up the database and test restoration | **Pass** (verified in Task 5) | `phase6-production-readiness.md` §3 — a `pg_dump`/`pg_restore` round trip against a disposable database, with the restored data and schema verified and a representative slice of the test suite run clean against it. |

## Summary

One real Fail: no rate limiting on login. Fixed in this task (see table row
above) with a RED→GREEN test, not left as a TODO. Every other bullet was
already correctly implemented across Phases 1–5 — this review's main value,
like Task 1's permission matrix, is converting "should be fine" into "proven,
with a citation," plus the one genuine gap it actually found and closed.
